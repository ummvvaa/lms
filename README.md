# Платформа подготовки к поступлению

Внутренняя платформа частной школы. Пять директоров ведут свои домены,
ученик видит свой кабинет. Данные заводятся импортом и руками, база
стартует пустой.

## Запуск с нуля

Всё, что нужно свежему клону, — заполнить два файла окружения. Ничего
из того, что не лежит в репозитории, руками доносить не требуется.

```bash
git clone <адрес репозитория> lms && cd lms
cp deploy/.env.example deploy/.env    # заполнить пароли и, если нужен ИИ, ключ модели
docker compose up
```

`docker compose up` из корня поднимает весь контур: корневой compose
делает `include` на `deploy/docker-compose.yml`. Миграции накатываются
сами при старте бэкенда (`backend/entrypoint.sh`), **данных они не
заводят** — после первого запуска в базе нет ни одного ученика.
В ней есть только справочники, посеянные миграциями: виды экзаменов,
типы документов эссе, категории ресурсов, бейджи, сюжеты главной,
правила обзвона и вопросы профтеста. Это части системы, а не выдуманные
люди (инвариант №8).

Фронт — http://localhost:5173, API — http://localhost:8000/api/,
документация API — http://localhost:8000/api/docs/.

Стартовый справочник вузов (20 записей с пометкой «не подтверждено»)
заводится отдельной командой, а не сам:

```bash
docker compose exec backend python manage.py seed_universities
```

Первая учётная запись в новом контуре создаётся из терминала — пароль
за человека никто не придумывает, приходит ссылка:

```bash
docker compose exec backend python manage.py invite_user --email you@school.kz --role admin
```

Учётные записи всех ролей для разработки заводит команда
`python manage.py create_dev_users` — только при `DEBUG=1`, пароли берутся
из `deploy/.env`. Отключённые администратором записи команда не включает
обратно: для этого нужен явный ключ `--force`.

Браузерный прогон ходит не под ними, а под **одноразовыми записями**
`*@probe.local`: `e2e/run.sh` заводит их перед прогоном
(`create_probe_users`, пароль из `PROBE_PASSWORD` в `e2e/.env`) и убирает
насовсем после (`purge_probe_users`) — даже если прогон упал или был
прерван. После прогона в системе не остаётся ни одной лишней записи;
журнал правок остаётся с подписью автора.

## Проверки

```bash
docker compose exec backend pytest          # тесты
docker compose exec backend ruff check .    # линтер
docker compose exec backend black --check . # форматирование
docker compose exec frontend npm run typecheck   # типы
docker compose exec frontend npm run lint        # eslint
docker compose exec frontend npm run build       # сборка
cp e2e/.env.example e2e/.env && cd e2e && npm install
cd e2e && npm test                          # браузерные сценарии (run.sh)
cd e2e && python3 api_probe.py              # прогон API под всеми ролями
```

### Эталоны сравнения раскладки

Сравнение раскладки (`e2e/tests/phase51.spec.ts`) сверяется со снимками
в `e2e/shots/baseline/`. Их **нет в репозитории** и не должно быть:
это десятки мегабайт PNG, которые к тому же зависят от сглаживания
шрифтов на конкретной машине. В свежем клоне этих проверок нет с чем
сравнивать, и они падают — это ожидаемо.

Эталоны снимаются заново на своей машине, до первой правки внешнего вида
и на том же посеве, что и последующий прогон. Порядок проектов задан
в `e2e/playwright.config.ts`: сквозной сценарий обнуляет базу, проект
`seed` наполняет её руками ролей через тот же API, что и экраны, и только
потом идёт всё остальное. Поэтому сначала обычный полный прогон, а следом
пересъёмка на получившемся посеве:

```bash
cd e2e
npm test                                                   # обнуление, посев, весь прогон
npm test -- --project=chromium --grep "раскладка" --update-snapshots
```

Порог расхождения задан долей (2%), а не нулём: сглаживание шрифтов даёт
фон само по себе. Расхождение выше порога — повод посмотреть глазами,
а не признак поломки.
