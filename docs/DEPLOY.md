# Развёртывание на боевом сервере

Инструкция для человека, который разворачивает контур с нуля и не помнит
подробностей. Контур поднимается через Docker Compose на любой машине
с публичным адресом: ничего специфичного для облака в файлах нет, всё,
что отличает одну машину от другой, живёт в `deploy/.env.prod`.

Где в тексте стоит `<…>` — параметр конкретной машины; заполняется после
развёртывания (см. раздел 10).

## 1. Требования к машине

| Что | Минимум | Зачем |
|---|---|---|
| Память | 4 ГБ | gunicorn на 4 воркера, Celery, Postgres и Redis вместе едят около 2 ГБ; остальное — запас на бэкап и сборку фронта |
| Процессор | 2 vCPU | сборка фронта и бэкап с проверкой идут параллельно с работой школы |
| Диск | 40 ГБ | база, загруженные файлы (материалы, документы портфолио), 7 + 4 бэкапа, образы. Смотреть: `df -h` |
| Система | Linux x86-64 (Ubuntu 24.04 LTS или Debian 12) | проверено на них |
| Установлено | Docker 24+ с Docker Compose v2, git | ничего больше: Python, Node, Postgres на машине не нужны |
| Сеть | публичный адрес, открытые наружу **80/tcp, 443/tcp, 443/udp** | 80 нужен для выпуска сертификата, 443/udp — HTTP/3 |
| Домен | A-запись на адрес машины | без домена Let's Encrypt сертификат не выпустит |

Параметры этой машины: `<адрес>`, `<тип машины>`, `<диск>`.

Проверка перед началом:

```bash
docker --version && docker compose version      # 24+ и v2
free -h && df -h /                              # память и диск
curl -4 -s ifconfig.me                          # публичный адрес
```

## 2. Порядок развёртывания

### Шаг 1. Код и окружение

```bash
sudo mkdir -p /opt/lms && sudo chown "$USER" /opt/lms
git clone <репозиторий> /opt/lms && cd /opt/lms
cp deploy/.env.prod.example deploy/.env.prod
chmod 600 deploy/.env.prod
```

Заполнить `deploy/.env.prod` — раздел 3 ниже. `deploy/.env.prod` в git
не попадает никогда: он в `.gitignore`.

### Шаг 2. DNS

A-запись домена (`SERVER_NAME`) должна указывать на адрес машины **до**
первого запуска: Caddy выпускает сертификат при старте, и если домен
смотрит не сюда, выпуск не пройдёт. Проверить:

```bash
dig +short <домен>      # должен вернуть адрес машины
```

### Шаг 3. Выкат

```bash
deploy/deploy.sh
```

Скрипт делает пять шагов в правильном порядке и останавливается на первой
ошибке:

1. собирает образы **без кеша** (`--no-cache`) — в фазе 55 кеш слоёв держал
   пакеты, удалённые тремя фазами раньше;
2. поднимает Postgres и Redis;
3. `manage.py check --deploy` — падает на слабом ключе, пустых хостах,
   стандартном адресе админки;
4. миграции и статика;
5. поднимает всё остальное.

Что поднимется: `postgres`, `redis`, `backend` (gunicorn), `celery-worker`,
`celery-beat`, `caddy` (TLS), `backup`. Контейнер `frontend-build` соберёт
статику фронта и завершится — так и задумано.

Обновление версии — та же команда: `git pull && deploy/deploy.sh`.

### Шаг 4. Сертификат

Ничего делать не нужно. Caddy при первом старте выпускает сертификат
Let's Encrypt на `SERVER_NAME` и дальше продлевает сам; HTTP перенаправляется
на HTTPS сам. Сертификат и состояние выпуска лежат в томе `caddy_data`
и переживают пересоздание контейнеров — лимит Let's Encrypt на перевыпуск
(5 в неделю на домен) при обычной работе не расходуется.

Убедиться:

```bash
docker compose -f deploy/docker-compose.prod.yml logs caddy | grep -i "certificate obtained"
curl -fsSI https://<домен>/healthz | head -1     # HTTP/2 200
```

Если сертификат не выпускается — раздел 6, «Caddy».

### Шаг 5. Первый вход

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend \
  python manage.py createsuperuser
```

Открыть `https://<домен>/<DJANGO_ADMIN_PATH>/` — это админка Django на своём
адресе (стандартного `/admin/` не существует). Дальше — в интерфейсе школы
`https://<домен>/`: экран «Пользователи», администратор заводит запись и шлёт
ссылку; пароль человек задаёт себе сам. Первого администратора можно завести
и из терминала — запись без пароля плюс приглашение на почту:

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend \
  python manage.py invite_user --email director@<домен школы> \
  --name "Имя Фамилия" --role admin
```

К этому моменту должна работать почта — раздел 7. Слова-пометки в имени
(«тест», «демо») система не примет.

**База стартует пустой** — это инвариант, выдуманных учеников нет.
Справочники, без которых экраны пусты (виды экзаменов, типы документов эссе,
бейджи, сюжеты главной, правила обзвона, вопросы профтеста), приезжают
миграциями. Данные заводятся импортом и руками.

### Шаг 6. Стартовый справочник вузов — по желанию

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend \
  python manage.py seed_universities
```

Заводит 20 вузов с программами, требованиями и раундами. Это **заготовка,
а не проверенные данные**: пороги и дедлайны помечены «не подтверждено»,
над ними висит оранжевая плашка, ученику процент соответствия показывается
с той же оговоркой. Снимает плашку директор по поступлению после сверки
с сайтом вуза. На непустом справочнике команда останавливается — досеять
поверх можно только явным `--force`. Убрать заготовку в бою — кнопка
«Удалить стартовый справочник» на экране «Справочник».

### Шаг 7. Проверка после выката

```bash
curl -fsS https://<домен>/healthz    # {"status":"ok"} — процесс жив
curl -fsS https://<домен>/readyz     # база и Redis доступны
curl -sk https://<домен>/admin/ | grep -c csrfmiddlewaretoken   # 0: по /admin/ отдаётся обычная страница фронта, админки Django там нет
docker compose -f deploy/docker-compose.prod.yml ps   # у всех healthy
docker compose -f deploy/docker-compose.prod.yml logs backup | tail -5   # «Бэкап проверен»
```

## 3. Переменные окружения

Полный список с пояснениями — `deploy/.env.prod.example`; что где взять
и что будет, если не заполнить, — `docs/ENV.md`. Здесь — только то, без чего
контур не поднимется или поднимется опасно.

| Переменная | Что это | Откуда взять |
|---|---|---|
| `SERVER_NAME` | домен без схемы | у регистратора домена |
| `CADDY_EMAIL` | почта для писем Let's Encrypt | рабочая почта администратора |
| `CADDY_TLS` | **пусто** в бою | локально — `tls internal` |
| `DJANGO_ADMIN_PATH` | адрес админки, одно слово без слэшей | придумать: `office-7f3a` |
| `DJANGO_ALLOWED_HOSTS` | домены через запятую | `school.kz,www.school.kz` |
| `CSRF_TRUSTED_ORIGINS` | те же со схемой | `https://school.kz,https://www.school.kz` |
| `FRONTEND_BASE_URL` | из него собираются ссылки в письмах | `https://school.kz` |
| `DJANGO_SECRET_KEY` | ключ подписи сессий, от 50 символов | `python -c "import secrets; print(secrets.token_urlsafe(64))"` |
| `POSTGRES_PASSWORD` | пароль базы | придумать длинный случайный; наружу база не смотрит |
| `SCHOOL_NAME`, `SCHOOL_SHORT_NAME`, `VITE_*` | название школы | как называется школа |
| `EMAIL_HOST`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL` | почта | кабинет сервиса рассылок, раздел SMTP |
| `BACKUP_REMOTE_BUCKET`, `_ENDPOINT`, `_REGION`, `_ACCESS_KEY`, `_SECRET_KEY` | куда уезжают бэкапы | кабинет хранилища — раздел 10 |
| `LLM_API_KEY` | ключ модели; пусто — работает правилами | кабинет провайдера |

Всё, что закомментировано в примере, имеет умолчание в коде. **Пустое
значение у такой переменной не равно умолчанию** — оно перебивает его пустой
строкой. Не нужно менять — не раскомментируйте.

## 4. Бэкапы

Контейнер `backup` ежедневно в `BACKUP_HOUR` (по умолчанию 03:00 по `TZ`)
и сразу после старта:

1. снимает дамп базы и **проверяет восстановление** во временную базу —
   непроверенный бэкап это не бэкап, а надежда;
2. складывает загруженные файлы (`media` и закрытый `private`) в архив
   и проверяет, что он читается;
3. в `BACKUP_WEEKLY_DAY` (воскресенье) откладывает копию в `weekly/`;
4. **выгружает** дамп и архив в объектное хранилище и проверяет, что размер
   в хранилище совпадает;
5. удаляет старое: ежедневные старше 7 дней, еженедельные старше 4 недель —
   и локально, и в хранилище.

Пока `BACKUP_REMOTE_BUCKET` пуст, бэкап остаётся только на машине, и в логе
об этом громко сказано. Бэкап на той же машине не спасает от потери машины.

Снять вручную и посмотреть, что есть:

```bash
docker compose -f deploy/docker-compose.prod.yml exec backup /scripts/backup.sh
docker compose -f deploy/docker-compose.prod.yml exec backup /scripts/restore.sh   # список локально и в хранилище
docker compose -f deploy/docker-compose.prod.yml exec backup cat /backups/verified.log
```

## 5. Восстановление из бэкапа — пошагово

Написано для человека, у которого что-то случилось и нет времени разбираться.
Каждый шаг — одна команда; если она не сработала, дальше не идти.

**Шаг 1. Не трогать базу до конца процедуры.** Остановить всё, что пишет:

```bash
cd /opt/lms
docker compose -f deploy/docker-compose.prod.yml stop backend celery-worker celery-beat
```

Пользователи в это время видят «нет связи с сервером». Это нормально.

**Шаг 2. Посмотреть, какие бэкапы есть.**

```bash
docker compose -f deploy/docker-compose.prod.yml exec backup /scripts/restore.sh
```

Команда печатает два списка: локальные и из хранилища. Имена вида
`lms-20260904-030000.dump` — дата и время снятия. Выбрать последний,
снятый **до** беды. Если машина новая и локальных нет — берите из хранилища,
скрипт скачает сам.

**Шаг 3. Восстановить.** Подставить имя файла из шага 2:

```bash
docker compose -f deploy/docker-compose.prod.yml exec backup \
  /scripts/restore.sh lms-20260904-030000.dump --force
```

Без `--force` скрипт только покажет, что нашёл, и остановится — так и задумано.
С `--force` он затирает текущую базу содержимым дампа и разворачивает файлы
из архива того же времени. В конце пишет «Восстановление завершено».

Если написал «файл не найден ни локально, ни в хранилище» — опечатка в имени,
вернуться к шагу 2.

**Шаг 4. Поднять обратно.**

```bash
docker compose -f deploy/docker-compose.prod.yml start backend celery-worker celery-beat
curl -fsS https://<домен>/readyz
```

**Шаг 5. Проверить глазами.** Войти, открыть список учеников, открыть одну
карточку и один загруженный файл. Данные — на момент снятия бэкапа: всё,
что вносили после, придётся внести заново.

### Восстановление на новой машине

То же самое, но перед шагом 2 — развернуть контур по разделу 2 (шаги 1–3)
с **тем же** `deploy/.env.prod`, включая `BACKUP_REMOTE_*`: тогда шаг 2
покажет бэкапы из хранилища, и шаг 3 скачает нужный сам.
`createsuperuser` делать не нужно — пользователи приедут в дампе.

## 6. Контейнер не поднялся

Сначала общее:

```bash
docker compose -f deploy/docker-compose.prod.yml ps            # кто в каком состоянии
docker compose -f deploy/docker-compose.prod.yml logs --tail=50 <служба>
```

**`backend` перезапускается по кругу.** В логе первая ошибка — обычно одна из:

- `ImproperlyConfigured: DJANGO_SECRET_KEY короче 50 символов` — сгенерировать
  ключ заново (раздел 3);
- `DJANGO_ALLOWED_HOSTS пуст` или `DJANGO_ADMIN_PATH пуст или равен «admin»` —
  заполнить;
- `Postgres не поднялся за 60 секунд` — смотреть `logs postgres`: чаще всего
  сменили `POSTGRES_PASSWORD` после первого запуска, а база в томе помнит
  старый. Либо вернуть пароль, либо (только на пустой базе!) снести том:
  `docker compose -f deploy/docker-compose.prod.yml down -v`.

**`caddy` не поднимается или сертификата нет.** `logs caddy`:

- `no such host` / `NXDOMAIN` — домен не смотрит на машину, проверить `dig`;
- `connection refused` на порту 80 — порт закрыт снаружи (фаервол облака
  или машины). Let's Encrypt ходит на 80, без него выпуска не будет;
- `too many certificates already issued` — исчерпан лимит Let's Encrypt
  (5 в неделю на домен). Ждать неделю. Бывает, если снести том `caddy_data`
  и поднять контур несколько раз подряд — не делайте так;
- `dependency failed to start: backend is unhealthy` — Caddy ждёт здорового
  бэкенда, смотреть `logs backend`.

**`frontend-build` упал.** `logs frontend-build`: обычно `npm ci` не смог
скачать пакеты (нет сети) или замок разошёлся с манифестом (`npm ci` требует
их согласованности — так и задумано, чтобы на сервере не собралось другое).

**`backup` пишет ошибку.** `logs backup`:

- `бэкап не разворачивается` — дамп битый, база в беде: смотреть `logs postgres`;
- `в хранилище файл другого размера` — обрыв при выгрузке, следующий запуск
  повторит; если повторяется — проверить ключи и бакет;
- `BACKUP_REMOTE_BUCKET пуст` — не ошибка, а предупреждение: бэкапы только
  на машине.

**Всё healthy, а сайт не открывается.** `curl -v https://<домен>/healthz`
с другой машины: если соединение не устанавливается — фаервол на 443;
если 502 — бэкенд не отвечает, `logs backend`.

**Ничего не помогло — откатиться.** `git checkout <предыдущий тег>` и
`deploy/deploy.sh`; миграции назад не откатываются, если новая версия их
добавила — тогда сначала восстановление из бэкапа (раздел 5).

## 7. Почта

Без работающей отправки нельзя пригласить ни одного человека: пароль никто
не задаёт за него, ссылка приходит письмом. Пока `EMAIL_HOST` пуст, письма
пишутся в журнал сервера, а у администратора на экране «Пользователи» висит
предупреждение.

| Переменная | Что это |
|---|---|
| `EMAIL_HOST` | SMTP-сервер сервиса рассылок |
| `EMAIL_PORT` | `587` для STARTTLS, `465` для SSL |
| `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` | логин и ключ, выданные сервисом |
| `EMAIL_USE_TLS` | `1` для порта 587 |
| `EMAIL_USE_SSL` | `1` для порта 465; TLS тогда выключается сам |
| `DEFAULT_FROM_EMAIL` | адрес отправителя; домен подтверждён у сервиса |

**Не берите логин и пароль ящика Microsoft.** Базовую аутентификацию SMTP
Microsoft отключает, и настройка перестанет работать в неизвестный день.
Нужен сервис рассылок (любой SMTP) и подтверждённый домен отправителя
(SPF и DKIM) — иначе письма уходят в спам.

Проверить:

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend \
  python manage.py check_mail --to вы@<домен школы>
```

То же есть в интерфейсе: экран «Пользователи», кнопка «Отправить пробное
письмо». Ссылка в письме ведёт не туда — проверьте `FRONTEND_BASE_URL`.

## 8. Что не работает в бою — намеренно

При `DEBUG=0` отказываются запускаться и флага «всё равно» не имеют:
`reset_data` (обнуление школы), `drop_seed_catalog` (снос заготовки —
в бою это кнопка на экране «Справочник»), `create_dev_users`,
`create_probe_users`, `dev_link`. Посевы браузерных прогонов
(`seed`, `baseline-seed`) в бою не работают потому, что без
`create_probe_users` некому войти, а запись `*@probe.local` в бою не
пускается ни паролем, ни по ссылке. `purge_probe_users` работает в любом
режиме — уборка должна быть возможна всегда; она удаляет только записи
`*@probe.local`, которых в бою нет.

Обнулить боевую базу командой нельзя. Если это действительно нужно —
восстановление из бэкапа (раздел 5) или ручная работа с базой.

## 9. Подключение модели, фоновые задачи, логи

**Модель.** Без `LLM_API_KEY` система работает правилами — это штатный режим.
С ключом проверить все операции разом:

```bash
docker compose -f deploy/docker-compose.prod.yml exec backend python manage.py check_llm
```

Поиск в интернете ходит только по белому списку — сайты вузов из справочника
и Common App; число из интернета без ссылки на официальный сайт не принимается.
Потолок расходов — `LLM_MONTHLY_LIMIT`; расходы видны на экране «Расходы на ИИ».

**Фоновые задачи.** `celery-beat` держит расписание (`CELERY_BEAT_SCHEDULE`
в `config/settings/base.py`): напоминания, сверка дедлайнов, пересчёт
готовности. Здоровье обоих контейнеров Celery видно в `ps`.

**Логи.** Всё пишется в stdout контейнеров, ротацию делает Docker: 20 МБ × 5
файлов на службу (`x-logging` в compose). `docker compose logs -f <служба>`.
Ошибки при заполненном `SENTRY_DSN` уходят в Sentry без персональных данных.

## 10. Временный контур в Google Cloud и переезд на казахстанский сервер

Этот раздел — **единственное** место, где упоминается облако. В файлах
контура (`deploy/`) ничего специфичного нет и быть не должно: на казахстанский
сервер едет ровно то, что обкатано здесь.

### Что настроено в Google Cloud

Машину создаёт владелец в консоли. Записать после создания:

| | |
|---|---|
| Проект | `<проект>` |
| Машина | `<имя>`, тип `<e2-medium или лучше>`, регион `<регион>` |
| Диск | `<40+ ГБ>` |
| Внешний адрес | `<статический адрес>` — обязательно **статический**: динамический сменится при перезапуске, и домен уедет |
| Правило фаервола | входящие `tcp:80,443` и `udp:443` со всех адресов; SSH — только со своих |
| Бакет для бэкапов | `<имя бакета>`, регион `<регион>`, доступ только по HMAC-ключу |

Бэкапы уходят в Google Cloud Storage по S3-совместимому протоколу.
В `deploy/.env.prod`:

```
BACKUP_REMOTE_BUCKET=<имя бакета>
BACKUP_REMOTE_ENDPOINT=https://storage.googleapis.com
BACKUP_REMOTE_REGION=auto
BACKUP_REMOTE_PROVIDER=GCS
BACKUP_REMOTE_ACCESS_KEY=<HMAC access key>
BACKUP_REMOTE_SECRET_KEY=<HMAC secret>
```

HMAC-ключ выпускается в консоли: Cloud Storage → Settings → Interoperability →
Create a key for a service account; у сервисного аккаунта роль только
`Storage Object Admin` на этом бакете.

### Что менять при переезде

Ровно `deploy/.env.prod` и DNS. В файлах — ничего.

1. На новой машине — раздел 2, шаги 1–2, с копией `deploy/.env.prod` со старой.
   Поменять в нём: `BACKUP_REMOTE_*` на хранилище нового провайдера
   (`_ENDPOINT` — его адрес, `_PROVIDER=Other`, ключи — его). Домен тот же.
2. На старой машине снять свежий бэкап: `exec backup /scripts/backup.sh`.
   Он уедет в **старое** хранилище; скачать оттуда дамп и архив файлов
   в `/backups` новой машины (`docker cp` в контейнер `backup`) — или временно
   указать на новой машине старые `BACKUP_REMOTE_*`, восстановиться и вернуть.
3. На новой машине — раздел 5 («Восстановление на новой машине»).
4. Переключить A-запись домена на новый адрес. Caddy на новой машине выпустит
   сертификат сам, как только домен на неё посмотрит (до этого в логе будет
   `NXDOMAIN` — это ожидаемо).
5. Старую машину остановить, но не удалять неделю: пока не убедились, что
   бэкапы на новой машине уезжают в новое хранилище (`logs backup`).

Что **не** переезжает и не должно: том `caddy_data` (сертификат выпустится
заново), `redisdata` (очередь и кеш — временное).
