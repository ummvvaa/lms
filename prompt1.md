Ты собираешь внутреннюю платформу частной школы, которая готовит учеников к поступлению в зарубежные вузы. Работа разбита на шесть фаз. **Пройди все шесть подряд, по порядку, не дожидаясь моих команд.**

Порядок фаз менять нельзя, перескакивать вперёд нельзя. Фаза считается завершённой только когда выполнены её критерии приёмки. Если фаза не проходит приёмку — чини её и не переходи к следующей: ошибка в ранней фазе разъезжается по всем последующим.

## Правило контекста — выполняется в каждой сессии

**В начале любой фазы:** прочитай `CLAUDE.md` и `docs/STATE.md`. Если их нет — ты в Фазе 1 и создаёшь их.

**В конце любой фазы:** перезапиши `docs/STATE.md` целиком (не дописывай), при необходимости добавь строки в раздел «Решения» в `CLAUDE.md`, сделай коммит с тегом фазы и выведи короткий отчёт — что сделано, что проверено, что осталось непонятным. После этого переходи к следующей фазе.

**Перед началом каждой следующей фазы перечитай `CLAUDE.md` и `docs/STATE.md` заново.** Не полагайся на то, что помнишь их с прошлой фазы: к четвёртой фазе ранний контекст уже вытеснен, а инварианты нарушать нельзя ни на одной из них.

`docs/STATE.md` — жёсткий лимит **50 строк**. Формат:

```
# Состояние проекта
Обновлено: <дата>   Последняя фаза: N — <название>

## Готово
- одна строка на завершённую фазу

## Сейчас работает
- 3–6 строк: что реально запускается и проверяемо

## Следующая фаза
- 2–4 строки

## Долги и известные проблемы
- максимум 5 строк, самое важное

## Открытые вопросы к владельцу продукта
- максимум 3 строки
```

Если файл вылезает за 50 строк — сокращай, а не расширяй. Детали живут в коде и в git-истории, не здесь.

`CLAUDE.md` создаётся в Фазе 1 и почти не меняется. Содержит: стек, структуру монорепо, конвенции, раздел «Инварианты» (см. ниже) и раздел «Решения» — по **одной строке** на архитектурное решение в формате `дата — решение — причина`.

## Стек

Монорепо. Python 3.12, Django 5 + DRF, PostgreSQL 16, Celery + Redis, React 18 + TypeScript + Vite, TanStack Query, TanStack Table, react-router. Разворачивается на своём VPS через Docker Compose.

```
/backend        Django-проект, приложения по доменам
/frontend       React + Vite
/docs           STATE.md и прочая документация
/deploy         docker-compose, nginx, .env.example
CLAUDE.md
prototype.html  кликабельный прототип — референс интерфейса
```

## Прототип в корне

`prototype.html` — согласованный с заказчиком кликабельный прототип. Открой и изучи его в Фазе 1, до написания моделей: он показывает состав экранов, набор полей по каждому домену, дашборды пяти директоров и кабинет ученика.

Что из него берём как обязательное:

- **Дизайн-система.** Оранжевый `#FF6A13` как акцент, тёплый графит `#231F1C` как базовый, молочный фон `#FBF8F4`, бирюза `#0E7490` и индиго `#4C5578` для графиков. Статусы: успех `#0F766E`, внимание `#B45309`, риск `#9F1239`. Обычный красный не использовать — рядом с оранжевым он не читается как тревога. Крупные скругления, мягкие тени, плашки-эмодзи над заголовками секций.
- **Состав экранов и набор полей** по каждому из пяти доменов.
- **Разделение того, что видит ученик и что видит директор** — прототип уже соблюдает инвариант №7.

Что из прототипа **не** переносим: сгенерированные данные (база стартует пустой), формулы статусов и весов Readiness (в проде они конфигурируемы), вёрстку как есть — React-компоненты пишем заново, прототип это макет, а не исходник.

Перенеси дизайн-токены в CSS-переменные фронта в Фазе 2, до появления первых экранов.

## Инварианты — нарушать нельзя

Продублируй их в `CLAUDE.md` и сверяйся с ними в каждой фазе.

1. **У каждого поля ровно один владелец-домен.** Пять доменов: `behavior` (Салтанат), `admission` (Асем), `exam` (Кымбат), `talent` (Арман), `sport` (Нурлыбек). Директор редактирует только свой домен, чужие поля видит, но не меняет.
2. **Реестр владения — один файл** (`backend/core/domains.py`). Из него питаются права DRF, валидатор предложений и генерация колонок на фронте. Нигде не дублировать.
3. **ИИ никогда не пишет в основные таблицы.** Только создаёт `Suggestion`. Применяет человек.
4. **Дедлайн принадлежит вузу, а не ученику.** Живёт в `AdmissionRound`. Меняется один раз — пересчитывается у всех.
5. **То, что имеет историю, хранится строками, а не полями.** Моки, соревнования, активности — дочерние таблицы с датами.
6. **Никакого JSONB для доменных данных.** Типизированные колонки: по ним строятся все дашборды.
7. **Ученику не показываются внутренние ярлыки** `critical`, `needs_supervision`, `A/B/C`, `strong/medium/weak`. Ни в API-ответах для роли «ученик», ни в интерфейсе. У ученика — задачи и процент готовности.
8. **База стартует пустой.** Никаких фикстур с выдуманными учениками. Данные заводятся импортом и руками.
9. **Всякое изменение доменного поля пишется в `AuditLog`** с указанием источника: `manual | import | ai | sync`.

## Общие требования к коду

Комментарии и docstring — по-русски, имена сущностей и полей — по-английски. Тесты на pytest с первой фазы: не гонись за покрытием, покрывай инварианты (права по доменам, применение предложений, расчёт соответствия). Миграции — по одной осмысленной на фазу. Секреты только через переменные окружения, `.env.example` держи в актуальном виде. После каждой фазы всё должно подниматься одной командой `docker compose up`.

# ФАЗА 1 — Фундамент и модель данных

Цель: поднимается пустая система с полной схемой БД и работающей админкой.

**Инфраструктура.** Монорепо по структуре выше. Docker Compose: postgres, redis, backend, frontend, nginx. Django-проект с настройками по окружениям. Линтеры: ruff + black на бэке, eslint + prettier на фронте. pytest с фикстурой БД.

**Модели.** Разложи по приложениям Django.

`accounts`: `User` (кастомная), `Identity` (provider, external_id, email — у одного пользователя может быть несколько: школьный Entra и личная почта для выпускников), `Role`.

`students`: `StudyGroup` (код, класс, 15–20 учеников), `Student` (ФИО, класс, группа, связь с User, год выпуска).

Пять профильных таблиц один-к-одному со `Student`:
- `BehaviorProfile` — посещаемость %, замечания, выполнение заданий %, статус `can_execute | needs_supervision | critical`
- `AdmissionProfile` — целевая страна, специальность, наличие Common App, наличие application account, статус `A | B | C`
- `ExamProfile` — IELTS текущий и целевой, SAT текущий и целевой, часов в неделю, преподаватель, GPA
- `TalentProfile` — основной трек, статус портфолио `strong | medium | weak`
- `SportProfile` — вид спорта, уровень, разряд, лидерская роль

Дочерние таблицы с историей:
- `ExamAttempt` — ученик, тип (IELTS/TOEFL/SAT/ACT), формат (mock/official), дата, общий балл, баллы по секциям
- `Activity` — ученик, категория (olympiad/project/research/startup/leadership/volunteering/competition/award), название, дата, описание, подтверждение
- `Competition` — ученик, соревнование, дата, результат, наличие сертификата

`universities`: `University` (название, страна, сайт, домен для сверки), `Program` (вуз, специальность, уровень), `AdmissionRound` (программа, тип ED/EA/RD/Rolling, дедлайн, источник, дата последней сверки), `StudentUniversity` (ученик, программа, tier `reach|target|safety`, статус заявки).

`core`: `domains.py` — реестр владения полями. Структура: домен → роль-владелец → модели → список редактируемых полей. `AuditLog` — actor, время, модель, объект, поле, старое значение, новое значение, источник, ссылка на предложение.

**Админка Django.** Настрой для справочников: вузы, программы, раунды, учебные группы. Это внутренний инструмент, красота не нужна, нужна работоспособность.

**Импорт.** Management-команда `import_students` — читает CSV/XLSX, создаёт учеников и профили. Без магии: явный маппинг колонок, отчёт об ошибках, идемпотентность по email.

**Документы.** Создай `CLAUDE.md` и `docs/STATE.md` по правилам выше.

**Критерии приёмки.** `docker compose up` поднимает всё. Миграции применяются на чистой БД. В админке заводится вуз с программой и раундом. Команда импорта заводит ученика из тестового CSV. Тест проверяет, что реестр доменов покрывает все редактируемые поля профильных моделей и что пересечений между доменами нет.

# ФАЗА 2 — Аутентификация, роли, права

Цель: люди входят под своими аккаунтами и видят только то, что им положено.

**Вход через Microsoft.** MSAL.js на фронте получает токен от Entra ID. Бэкенд проверяет подпись по JWKS, сверяет issuer, audience и срок, достаёт email и группы, находит или создаёт `User` и `Identity`, выдаёт **свою** сессию через httpOnly cookie. Токен Microsoft на последующих запросах не используется и в localStorage не хранится.

**Роли из групп Entra.** Маппинг групп на роли при каждом входе, конфигурируемый через настройки. Роли: `student`, `director_behavior`, `director_admission`, `director_exam`, `director_talent`, `director_sport`, `admin`.

**Вторая дверь для выпускников.** Вход по личной почте с одноразовой ссылкой — для тех, у кого школьный аккаунт отключён. Привязка второй `Identity` к существующему `User` из кабинета.

**Права.** DRF-permissions, построенные на реестре доменов: на запись поля проверяется, принадлежит ли оно домену роли. Ученик читает только свой профиль. Директор читает всех, пишет только свой домен. `admin` (директор школы) читает всё и пишет свой домен.

**Фильтрация ответов для ученика.** Сериализаторы для роли `student` не отдают поля-ярлыки из инварианта №7. Это делается на бэкенде, а не сокрытием на фронте.

**Аудит.** Middleware или сигналы, пишущие каждое изменение доменного поля в `AuditLog`.

**Фронт.** Каркас React: вход через MSAL, layout с боковой навигацией по ролям, роутинг, TanStack Query, генерация TypeScript-типов из OpenAPI-схемы DRF. Пустые экраны-заглушки под будущие дашборды.

**Критерии приёмки.** Тест: директор экзаменов получает 403 при попытке записать поле домена поступления. Тест: ученик не видит поля `behavior_status` и `admission_status` в своём ответе API. Вход и выход работают, сессия переживает перезагрузку страницы.

# ФАЗА 3 — Рабочие экраны

Цель: система становится пригодной для ежедневной работы пяти директоров.

**API.** CRUD по каждому домену. Батч-эндпойнт для массового сохранения: принимает список изменений, валидирует домен, применяет транзакцией, пишет аудит. Пагинация, фильтры по группе, классу, статусам, поиск по имени.

**Табличный режим.** Плотная таблица: строки — ученики, колонки — только поля домена текущей роли (берутся из OpenAPI, а не хардкодятся). Редактирование в ячейке, переход по Tab, вставка из буфера сразу в несколько ячеек. Изменения копятся в локальном черновике, уходят одним батч-запросом по кнопке «Сохранить». Индикатор несохранённых изменений, предупреждение при уходе со страницы.

**Карточка ученика.** Все пять доменов на одной странице. Свой домен редактируется, чужие показаны с подписью «ведёт: <имя директора>». Вкладка истории изменений из `AuditLog`.

**Дашборды.** Пять штук по одному на роль, плюс сводный для директора школы. Содержание берётся из технического задания школы: у Салтанат — заполненность профилей, светофор, риски по посещаемости; у Асем — счётчик слотов, распределение A/B/C, календарь дедлайнов, списки без Common App; у Кымбат — матрица шести корзин по IELTS и SAT, кандидаты в TOP-30, падения моков; у Армана — распределение портфолио, разбивка по шести трекам, обратный отсчёт до 1 ноября; у Нурлыбека — перспективные спортсмены, календарь соревнований, статус сертификатов.

**Readiness Score.** Расчёт на бэкенде в одном модуле, отдаётся вычисляемым полем. Веса конфигурируемы через настройки, не зашиты в код. Слабое звено определяется по количеству восстановимых баллов — то есть `(100 − значение) × вес`, а не по самому низкому проценту. Таблица `ReadinessSnapshot` для еженедельных срезов и графиков динамики.

**Импорт из файла.** Загрузка XLSX/CSV через интерфейс: предпросмотр, сопоставление колонок с полями своего домена, отчёт о конфликтах, применение.

**Критерии приёмки.** Директор заполняет 20 учеников через таблицу, сохраняет одним запросом, изменения видны в аудите. Дашборд грузится меньше секунды на 250 учениках. Ученик открывает свой кабинет и видит Readiness Score без внутренних ярлыков.

# ФАЗА 4 — Требования вузов, соответствие, роадмап

Цель: система отвечает на вопрос «куда я прохожу по баллам и чего не хватает».

**Справочник требований.** Модель `AdmissionRequirement`: программа, минимальный GPA, минимальный IELTS и TOEFL, минимальный SAT и ACT, требуемые предметы, требования к портфолио, примечания, источник и дата актуализации. Это ровно те таблицы, которые директор по поступлению уже ведёт в своих файлах — предусмотри импорт из XLSX с сопоставлением колонок.

**Движок соответствия.** Сервис, который по профилю ученика и требованиям программы возвращает: проходит / не хватает, и по каждому критерию — текущее значение, порог, разрыв. Результат вычисляемый, не хранимый, кэш по необходимости.

Два направления работы:
- по ученику — как он выглядит на фоне своего списка вузов
- по требованиям — какие программы открываются при текущем профиле и какие откроются, если поднять IELTS на 0.5

**Экран ученика «Мои вузы».** По каждой программе — статус соответствия и конкретный разрыв: «не хватает 0.5 IELTS и 60 SAT». Формулировки конструктивные, без ярлыков.

**Роадмап.** `TaskTemplate` — шаблоны задач по потокам, заводятся директором. `Task` — задача ученика: название, категория, приоритет, дедлайн, статус `todo | in_progress | review | done`, автор, комментарии. Генерация задач из шаблона потока и из дедлайнов вузов, куда ученик подаётся. Два представления на фронте: таймлайн по месяцам и доска по статусам.

**Эссе.** `Essay` — ученик, программа (или общее), тип, версии текста, статус `draft | review | revision | done`, комментарии куратора. Редактор без ИИ-генерации: на этой фазе ИИ к эссе не подключается вообще.

**Критерии приёмки.** Импортируется файл требований, и по ученику с IELTS 6.0 система показывает, какие программы открыты, какие закрыты и на сколько. Задача, созданная из дедлайна вуза, появляется в роадмапах всех, кто туда подаётся. Сдвиг дедлайна в справочнике сдвигает задачи.

# ФАЗА 5 — Движок предложений и ИИ

Цель: директор вводит данные текстом и файлами, а не по одной ячейке.

**Движок предложений.** `Suggestion` — автор, роль, команда, тип источника, статус `draft | pending | applied | partially_applied | rejected | reverted`. `SuggestionChange` — ученик, модель, поле, старое значение, новое значение, уверенность, ссылка на источник, флаг принятия.

Применение — одна транзакция: проверить, что старое значение всё ещё актуально (иначе пометить конфликт и пропустить), записать новое, создать запись аудита со ссылкой на предложение. Откат — обратный набор изменений, тоже через аудит.

Валидатор на создании: строки с полями чужого домена отбрасываются на сервере. Не в промпте — в коде.

**Экран предпросмотра.** Таблица изменений с сортировкой по уверенности: сомнительное сверху. Галочки для частичного принятия. Кнопка «принять все выше порога» — отдельным явным действием с записью в журнал. Показ источника по каждой строке.

**Сопоставление имён.** Отдельный сервис. Данные придут на русском, казахском и английском, со склонениями, инициалами и однофамильцами. Нужен матчер с оценкой уверенности и интерфейс разрешения неоднозначностей — «нашлось двое, выберите». Это главный источник тихих ошибок, отнесись серьёзно и покрой тестами.

**Celery.** Все вызовы модели и разбор файлов — фоновые задачи. Эндпойнт возвращает id задачи, фронт опрашивает статус, показывает прогресс.

**Инструменты модели.** Типизированные функции, не свободный доступ к БД: найти ученика по имени, предложить изменение поля, разобрать текст в записи, получить требования программы, создать задачи группе. Каждый вызов проверяется против роли вызывающего.

**Кнопки в интерфейсе.** Не чат, а именованные действия. Общие для всех директоров: «Вставить как есть» (текст из мессенджера или письма → разбор → предпросмотр), «Загрузить файл», «Массовое действие» над выделенными учениками, «Дайджест на сегодня», «Объясни этот список».

Специальные по ролям: у Асем — «Разобрать вуз» (название или ссылка → раунды, дедлайны, требования) и «Проверить баланс списка reach/target/safety»; у Кымбат — «Разобрать мок» (баллы или скрин → секции, сравнение с прошлым) и «План подготовки»; у Армана — «Разобрать активность» (описание → категория, сила, чего не хватает) и «Gap → задачи»; у Нурлыбека — «Распознать сертификат» (фото → соревнование, дата, результат).

**ИИ объясняет соответствие.** По ученику и программе — человеческим языком, чем именно он не дотягивает и что даст наибольший прирост шансов. Опирается только на данные из `AdmissionRequirement`, ничего не выдумывает. Если требований в справочнике нет — так и говорит.

**Ограничение по эссе.** ИИ не пишет и не переписывает текст эссе. Разрешено только задавать ученику вопросы, помогающие раскрыть историю. Вся активность ученика с ИИ по эссе видна куратору.

**Персональные данные.** В модель уходят только поля, нужные конкретной задаче, а не профиль целиком. Режим без хранения запросов на стороне провайдера. Каждый вызов логируется: кто, что отправлено, что вернулось.

**Критерии приёмки.** Директор экзаменов вставляет кусок переписки с баллами восьми учеников и получает предпросмотр, где двое помечены как неоднозначные. Принимает шесть из восьми — применяются только они. Откат возвращает прежние значения. Тест: предложение с полем чужого домена отбрасывается.

# ФАЗА 6 — Выпускники, фоновая сверка, продакшн

Цель: замыкается сеть выпускников и система готова к боевой эксплуатации.

**Выпускники.** `Alumnus` — связь со `Student`, год выпуска, вуз, программа, страна, текущее занятие, согласие на менторство, профиль на момент поступления (GPA, IELTS, SAT, активности) и результат по каждой заявке. Каталог с фильтрами по стране, вузу, специальности, году.

**Менторство.** `MentorshipRequest` — запрос ученика проходит через сотрудника школы, а не напрямую к выпускнику. Статусы, история встреч.

**Архив эссе выпускников.** Только с явного согласия, с указанием, куда человек поступил. Доступ на чтение для учеников.

**Переход ученик → выпускник.** За два месяца до выпуска — предложение привязать личную почту второй идентичностью. Автоматический перевод роли по дате выпуска.

**Фоновая сверка дедлайнов.** Периодическая задача Celery обходит официальные сайты вузов по **белому списку доменов** (только сайты вузов и Common App, никаких форумов и агрегаторов). Каждый извлечённый факт хранит ссылку, дату и фрагмент-источник. Расхождения складываются в `Suggestion` для директора по поступлению. Без источника поле не меняется.

**Дайджест.** Ежедневная сводка изменений по домену каждого директора, открывается при входе.

**Продакшн.** Docker Compose для боевого контура: gunicorn, nginx с TLS, отдельные контейнеры Celery worker и beat. Автоматические бэкапы Postgres с проверкой восстановления. Healthcheck-эндпойнты. Sentry или аналог. Ротация логов. Инструкция по развёртыванию в `docs/DEPLOY.md`.

**Критерии приёмки.** Фоновая задача находит изменившийся дедлайн и создаёт предложение со ссылкой на источник. Запрос на менторство доходит до выпускника только после одобрения сотрудником. Бэкап снимается и разворачивается на чистой машине.

Проходишь все шесть фаз подряд. После каждой: перезаписываешь `docs/STATE.md`, при необходимости добавляешь строки в «Решения» в `CLAUDE.md`, коммитишь с тегом фазы, выводишь короткий отчёт — и идёшь дальше.
